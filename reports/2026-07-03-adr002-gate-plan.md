## The SS9 gate, restated exactly

**Load-bearing claim:** behaviour can ground a brain-hypothesized ontology beyond walkability (a HUD/life
detector; entities).
**The probe:** a brain hypothesizes "region R = my life"; its grounded life-detector is scored against the
RAM `hp` oracle as it plays/fights.
**PASS** requires BOTH arms:
  (a) it grounds the truth — the detector's reading tracks the oracle's hp value across a run.
  (b) it rejects a decoy — handed a plausible-but-wrong region (a score/enemy counter, a static UI box),
      the loop discards it because its firing fails to correlate with the consequence.
**FAIL** = the direction dies cheap, here, before any rewrite.

SS9 as written has no metric/threshold/run-length (flagged as still-a-vibe by roadmap-v2 Phase B). This
pass PINS one (see "Threshold" below) so the gate is actually runnable and falsifiable, per SS11's
"a gate that can't fail" tripwire.

## The 0xC120-vs-0xD389 oracle verdict

**`0xC120` read as BCD is correct. `0xD389` is WRONG.** Confirmed against `runs/2026-06-26_cavenoire_combat_auto`
(2000-frame recorded combat run, `ram.bin` + `oracle.jsonl`, gitignored — not the full source, but this
pass regenerated the check against it):

- Visible HP at frame 459 = 6/10, frame 478 = 2/10, frame 516 = 1/10 (screenshots read directly).
- `0xC120` raw bytes at those frames: `0x6`, `0x2`, `0x1` — as BCD: 6, 2, 1. **Exact match, every frame.**
- `0xD389` raw byte at all three frames: `7` (stuck) — does not track HP at all in this recording.
- Over the full 2000-frame run, `bcd(0xC120)` distinct values = `{0,1,2,4,5,6,7,8,10}` (all in-range,
  smooth); `0xD389` distinct = `{0,4,5,7,8,10}` (missing 1,2,6 entirely — inconsistent with a byte tracking
  HP through combat where those values clearly occur per the digit-read anchors above).
- The `eval/fixtures/cavenoire_hp_oracle` 2-anchor fixture (HP 7 and 10) **cannot distinguish the two
  addresses** — both `0xC120`-as-BCD and `0xD389`-as-raw-decimal happen to equal 7 and 10 at those two
  points. The disambiguation needed a 3rd, richer data point (the combat run), not more anchors on the
  same 2-frame fixture.
- `world_mcp.py`'s `GAMES["cave_noire"]["watch"]` already uses `0xC120` (correct, comment says BCD).
  **`play_cave_noire.py` line ~40 still hardcodes `watch={..., "hp": 0xD389}` — the WRONG oracle.** Not
  fixed here (guardrail: no brain/perceiver edits in this pass) — flagged for a follow-up one-line fix.
  `eval/_archive/find_hp_addr.py` also does raw (non-BCD) byte matching, so it will find `0xD389` on a
  2-anchor fixture designed only for {7,10} — a decimal/BCD-blind matcher can't tell them apart; it would
  need a BCD-aware variant or a 3rd anchor to also disambiguate.
- Memory note `cave-noire-hp-oracle.md` ("HP is BCD at 0xC120; Phase A's 0xD389 is WRONG") is **confirmed
  correct** by this pass. The Phase A precheck doc's `0xD389` claim is superseded/wrong.

## Offline harness: `eval/score_hud_grounding.py`

Given recorded frames + `ram.bin`, decodes the `hp` oracle (BCD @ `0xC120`, clamped to [0,10], out-of-range
= skipped as transition garbage — same discipline as the Phase A precheck). Candidate detector
(`RegionDigitDetector`): a fixed pixel box (bottom status bar, no segmentation, per roadmap-v2 Phase B's
"no segmentation in Rung 0" rule) + a 0-9 glyph-template bank self-calibrated from a handful of the SAME
run's own frames at known-value anchors (the oracle scores; it never becomes an agent input — consistent
with SS11's no-leak tripwire). Scores TWO regions per run: the real HUD "current HP" box (truth arm) and
the ENEMY-counter box (decoy arm, per Phase A's enumerated decoy set).

**Pre-stated threshold (pinned by this pass, since SS9 as written has none):**
PASS = truth-region exact-value agreement >= 0.90 **AND** decoy-region agreement <= 0.50 **AND**
(truth agreement − decoy agreement) >= 0.30. Both arms required, matching SS9's letter.

### Baseline result (`runs/2026-06-26_cavenoire_combat_auto`, 2000 frames, real recorded combat)

```
TRUTH region:  agreement = 0.362  (2000 scored frames)
DECOY region:  agreement = 0.000  (2000 scored frames)
ARM (a) grounds truth (>=0.90):                 FAIL
ARM (b) rejects decoy (<=0.50 AND gap >=0.30):  PASS
GATE: FAIL
```

**This is a genuine baseline, not a rigged one.** Inspecting mismatches: the crude single-vs-double-digit
split misreads "10" as "20" (glyph-bank calibrated only on single digits, so the leading "1" of "10"
sometimes matches the "2" template); single digits occasionally read `None` under HUD-overlay/menu-frame
noise. Both are real, fixable weaknesses of a NAIVE hand-written detector — not scoring-harness bugs (spot
checks against ground-truth screenshots confirm the oracle values are right; the detector's readings are
demonstrably wrong at those frames). **There is real headroom**: a naive region-reader does NOT already
pass; getting from 0.36 to 0.90 needs an actual digit-count-aware / better-calibrated reader, which is
exactly the kind of grounding work a real hypothesize->ground->compile loop would have to do (and might
fail to do on its first hypothesis — which is what arm (a) is FOR).
The decoy arm passes cleanly (0.0 agreement — the ENEMY counter never matches the hp oracle by chance, so
a real loop would reject it). That arm's easiness is expected: an ENEMY count and an HP count rarely
collide in value; the real risk in a live run is a decoy that's ALSO digit-shaped and coincidentally
correlated more often (e.g. a floor counter that also decreases) — worth choosing carefully in Phase D.

## What remains: the smallest paid run that would settle the gate

The offline half (this pass) proves the SCORE is computable and gives a real number for one hand-written
candidate. It does **not** answer the SS9 question, which is about a **brain's own hypothesis**, not a
human's. The minimal remaining paid run (Phase D):

1. Add the 2-3 primitives the probe needs to `world_mcp.py`: `read_text` (or a region-crop-and-return-pixels
   tool, whichever is cheaper to wire), `whats_changed` (frame-diff over a region), and expose the HP
   oracle ONLY as `oracle.jsonl` (never on the wire — unchanged from today).
2. One live Claude-over-MCP session (`../aria-mcp-test/` per the Phase A doc's launcher note) plays a short
   Cave Noire combat segment, HYPOTHESIZES a region ("that box top-left is my life"), and its grounded
   detector (however IT builds one, not `RegionDigitDetector`) is scored by `eval/score_hud_grounding.py`
   (or a live variant of it) against the same `0xC120` BCD oracle.
3. Hand the SAME brain a decoy region (ENEMY counter or floor number) and confirm it discards it (arm b).
4. Apply the threshold pinned above (or a revised one, decided BEFORE the run, per SS11's "pick the
   metric, hold the unit, let it fail" tripwire) to call PASS/FAIL.

This is genuinely the smallest paid unit: **one short session, one hypothesis, one decoy, scored against
an oracle that already exists.** Cost is bounded by session length, not by anything this pass needs to
build further.

## Honest uncertainty

- The 0.36 baseline is for ONE naive detector design; a smarter offline candidate (e.g. one that first
  counts glyph-width before matching) would likely score higher without needing a live brain at all — this
  pass didn't chase that, since the point was to prove the harness runs and get *a* real number, not to
  optimize the hand-written stand-in (SS11: don't hand-code a bespoke perceiver here — the loop is the
  deliverable, not a tuned detector).
- The pinned 0.90/0.50/0.30 threshold is this pass's best-effort operationalization of SS9's vague language,
  not a number handed down by the ADR. It should be sanity-checked (or explicitly re-affirmed) before the
  paid Phase D run is scored against it, per roadmap-v2 Phase B's instruction to pin the metric "after Phase
  A, since the numbers depend on how often life changes" — this pass had the combat run's actual dynamics
  available and used them, but a reviewer should double check the threshold isn't accidentally tuned to
  make THIS run's baseline look a particular way.
- `eval/fixtures/cavenoire_hp_oracle`'s 2 frames are both non-gameplay (item-menu) HUD layout (HP at
  TOP of screen), not the bottom in-dungeon status bar Phase A Check 1 and this pass's harness assume.
  It's fine as the `find_hp_addr` uniqueness fixture (its original purpose) but is NOT a usable input to
  `score_hud_grounding.py` beyond a smoke test (only 2 frames, wrong HUD region) — a reviewer should not
  mistake the tiny committed fixture for a sufficient replacement of the full recorded run.
