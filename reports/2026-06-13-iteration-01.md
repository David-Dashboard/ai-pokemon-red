# Iteration 01 — Baseline: can a small LLM agent play Pokémon Red? (2026-06-13)

## North star (why this project exists)
Build an agent that **iteratively improves** and **generalizes across games — and eventually
reality.** The agent's "brain" is fully decoupled (ai-aria) from the world it acts in (here a Game
Boy, via ai-pokemon-red). Pokémon Red is just the first probe world: cheap, well-understood, a
stand-in for "an arbitrary new environment."

Hard-mode constraints we are deliberately aiming for:
- **Generalize:** find the *smallest* increments that let the *same* agent play *other* games (then
  real tasks) — not Pokémon-specific hacks.
- **No ROM / privileged state, ideally:** lean on what any environment offers (the **screen**) rather
  than a game-specific RAM memory map. RAM won't exist in a new game or in reality — it's a crutch.
- **Cheap:** minimize API calls / token cost. Prefer small or off-the-shelf models; call an expensive
  brain only when truly needed.

## This iteration — scope & hypothesis
- **Scope:** stand up the decoupled stack and get a **baseline** read of a small, cheap model
  (Claude Haiku 4.5) playing Pokémon Red via vision.
- **Hypothesis:** a capable-but-small VLM, given the screen + a tight action contract, can make
  reliable forward progress in the overworld.

## What we built
- **Decoupled integration:** ai-pokemon-red `--backend aria` → ai-aria's OpenAI-compatible endpoint
  (bearer-authed, vision-capable). No shared code; the brain is a separate service.
  - Branches: ai-pokemon-red `feat/aria-backend`; ai-aria `feat/decouple-instructions-block`
    (companion refactor) + `pokemon-red-constitution` (the game agent "Red", rebased on it).
- **Repurposed the companion into a game agent ("Red"):** rewrote its constitution
  (persona/place/goals/core_memory/lessons) and **decoupled the hardcoded instructions block** so the
  harness's memory protocol is persona-neutral and reusable for non-companion deployments.
- **Tooling:** `make_state.py` (robust intro-skip → `start.state`; fixes a name-entry bug in
  `new_game.py`), `eval_haiku.py` (Docker-free direct-API harness).
- **Under test:** Haiku via LiteLLM; vision = the **native 160×144 Game Boy frame** as a base64 image,
  alongside RAM-derived text state and wall-bump feedback.

## Method
Ran episodes from a past-the-intro start state (the bedroom), vision on, through the live aria stack.
Observed: the THINK/MOVE trace, RAM-derived state (map/x/y/HP/badges), new-map-discovery reward, and
the agent's own written memory (`aria-data/core_memory.md`, `notes.md`, `journal/`).

## Results (issues)
**Works**
- Follows the THINK/MOVE contract 100% of the time; honors multi-tile moves; uses wall-bump feedback
  to adapt.
- Tracks RAM-grounded facts correctly (position, money ¥3000, badges 0) and even **deduced the room's
  wall boundaries** from coords + feedback.
- The **memory system works flawlessly** — Red autonomously wrote 20 structured core-memory updates +
  notes + a rolling recap, unprompted.

**Breaks — all rooted in vision on 160×144** (quotes are Red's own memory):
- **Confabulated geography:** labeled the bedroom (map 38) "Oak's Lab interior."
- **Phantom NPCs:** invented "two NPCs," "talked to" them, filed them as fact (they are furniture —
  bed, PC, SNES).
- **Fabricated success:** wrote *"Lab successfully exited via stairs at (4,7). Entering new map area"*
  — it never left map 38 (100/100 steps). Hallucinated progress, committed to long-term memory.
- **Instruction override:** the prompt says *"do NOT press A in an empty room"*; it pressed A at the
  imaginary NPCs anyway. Perception beat instruction.
- **Net:** in a 100-step run it **never escaped the first room.** A separate 16-step run *did* reach
  the next map — i.e., success is luck-dependent, not reliable.

**Process issues found**
- `ARIA_DATA_DIR` was unset → ran on the default `aria-data/`, so Red's **seeded** game knowledge
  (type chart, play-lessons, mission tier) was never loaded. *Nuance:* the harness prompt already
  carried the movement rules and it still failed → the bottleneck is **perception, not knowledge.**
- **Memory bled across runs** (no fresh data dir per episode) → neither run was a clean trial.
- **0 `<lesson>` writes:** Red used core_memory as a status board and never distilled a durable
  lesson → the learning loop produced no cross-run improvement yet.

## Conclusions
1. **The fault line is perception.** Anything from RAM → correct; anything read from pixels →
   confabulated. The 160×144, 4-shade tile screen is out-of-distribution for the VLM.
2. **The harness + memory machinery is solid** and faithfully records whatever the model believes —
   so a perception-limited model yields a tidy, confident, *wrong* worldview. **Faithful memory
   amplifies bad perception.**
3. **Tension with the north star:** "it works at all" currently depends on the **RAM crutch**
   (position + wall-bump feedback) that we explicitly want to drop for generalization. Dropping RAM
   makes it harder exactly where the model is weakest. So **perception is the generalization
   bottleneck** and is where the next increments must go.
4. **Planning is *not* the bottleneck** (Haiku nails the contract and reasons fine over good state).
   So "use a bigger/more expensive brain" is not the obvious first lever — fixing perception is.

## Next iteration (prioritized by leverage × cheapness × generality)
**A. Improve perception cheaply — highest leverage**
- **Frame preprocessing (near-free):** upscale 3–4× nearest-neighbor, palette-normalize, optionally
  overlay a coordinate/tile grid. Directly attacks confabulation; trivial token cost.
- **Perception-as-a-module (the generalization bet):** insert a dedicated *screen → symbolic state*
  step BEFORE the planner. Options on a cheap→general axis:
  - *Classical CV / tile template-matching* — extract a symbolic grid with **no API calls and no ROM**.
    Generalizes across tile-based games; near-free; but not to arbitrary/real scenes.
  - *Small local off-the-shelf VLM* (quantized ~2–7B) as the perception layer → structured state,
    **replacing the RAM map**. Broad generality, runs locally (cheap), off-the-shelf — the user's
    "pre-trained off-the-shelf model" idea applied to *perception*, not planning.
  - Reserve the LLM brain for *planning over symbolic state* → far fewer, cheaper calls.

**B. Cut cost / API calls**
- Scripted/heuristic traversal for routine movement; invoke the brain only at decision points or when
  "stuck" (position unchanged for N turns).
- Don't re-query on unchanged frames; cache perception.

**C. Clean the evaluation**
- Fresh `ARIA_DATA_DIR` per run; point it at the game seed.
- Define a tiny benchmark: time-to-leave-house, maps-discovered / 100 steps, first-battle outcome —
  averaged over N seeds.
- A/B: Haiku vs Sonnet vs (perception-module + Haiku-planner).

**D. Toward "no ROM"**
- Replace RAM-derived state with the perception module's output; keep RAM **only as an eval oracle**
  (to score perception accuracy), never as an agent input. This is the concrete first step to
  generalize off Pokémon.

## Open question for Iteration 02
Which perception substrate gives the best **generality-per-dollar**: classical tile-matching (free,
tile-games only) vs a small local VLM (general, cheap-ish, off-the-shelf)? Iteration 02 = build the
**perception-as-a-module seam** + the clean eval, and A/B these — treating RAM as oracle only.
