## 3. Fix (a): pre-approach NEAR discipline (decision of record)

**Why v3's prose failed, precisely.** The instruction was buried in cycle sub-step 3(i), phrased
conditionally ("if near"), stated no consequence, and framed NEAR as an *observation* ("record that it's
near") rather than a *pre-commitment* ("declare it near BEFORE you go"). A model under load drops a
soft, consequence-free, conditional sub-step.

**The v3.1 brief change (three levers, all prose but materially restructured):**
1. **Hard ordering, not a sub-step.** The brief states as a top-level rule: *you may not call
   `run_skill approach_suspect` unless your immediately-preceding action logged a `NEAR` (or an explicit
   `FAR` not-near note) for the suspect at the current step.* NEAR-before-approach becomes the cycle's
   spine, not an optional courtesy inside it. **The `FAR` line is a discipline device, deliberately
   scorer-invisible — verified against the frozen scorer:** `eval/score_entity_gate_v3.py:391` counts a
   line as malformed only if it contains the literal token `ENT|NEAR|DECLARE|REJECT`; a `FAR id=<k>
   step=<n>` line matches none of the claim regexes (`_NEAR_RE` requires the literal `NEAR`) and none of
   the malformed tokens, so it is silently ignored — it inflates neither `malformed` nor `n_lines`, and
   touches no scored quantity. It forces the brain to LOOK-and-decide before approaching without adding
   a scored claim. (This is why prong (a)'s fix needs no scorer edit — the machinery-frozen claim holds
   at the line level.)
2. **Name the exact v3 failure + its cost.** The brief tells the brain what went wrong last time and what
   it cost: NEARs logged after the hit covered nothing, `q_k` starved to 0.400, the whole paid run was
   wasted. A named, quantified prior failure is a stronger signal than a neutral instruction.
3. **Worked coverage micro-example.** The brief shows why skipping is never worth it: the approach is
   1–2 steps, `W=15`, so a NEAR logged the instant before you approach covers any drop in that approach
   with 14 steps to spare.

**Anti-thrash accounting + the pre-registered escalation ladder.** PROTOCOL §6 forbids running an
identical failed action again. This attempt is NOT identical: the brief is restructured (hard ordering +
named consequence), and fix (b) changes the cycle geometry the NEAR sits in. But honesty requires
naming the risk: **this is the SECOND prose attempt at prong (a), and prose is the weakest enforcement
rung** (`PROTOCOL.md`/`THEORY.md`: ~80% adherence). So the escalation is pinned NOW, not improvised
later:

> **v3.2 escalation (pre-registered, NOT built here):** IF v3.1 again lands INSUFFICIENT_DATA or a
> `q_k` starved by trailing NEARs (prong (a) recurs), v3.2 adds a MECHANICAL, stricter-only world-side
> guard — `run_skill("approach_suspect")` returns an error and consumes no world-step unless a
> watermark-advancing look (`read_region`/`whats_changed`) on the suspect's box was the brain's most
> recent prior tool call. This makes the pre-approach look an INVARIANT (the non-drift thesis:
> invariants in code, not prompts), a code build with its own free gate (the guard fires / rejects
> correctly on canned frames) and PR. It is stricter-only (`run_skill` gains a precondition; nothing
> loosens).

Testing the cheap rung once more before the code build is deliberate, not lazy: (1) v3's prose was
genuinely weak (buried, conditional, consequence-free) — a sharply rewritten brief is a real, different
lever; (2) the mechanical guard carries its own risk (it could reject a legitimate re-approach, or
interact with the macro-interior exclusion) and is worth deferring until proven necessary; (3) the paid
run is `~$5`. If prong (a) recurs, v3.2 is already written down. **This is the one decision in this doc
worth a reviewer's and David's explicit eyes** — the alternative (go mechanical now) is defensible.

## 4. Fix (b): distance invocation (decision of record)

Prong (b) is genuinely NEW guidance — the v3 brief never told the brain WHERE to stand when invoking the
macro — so it is not an anti-thrash repeat.

**The v3.1 brief change:**
1. **Approach only from a visible gap.** The brief pins: only call `approach_suspect` when there are
   several tiles of separation between you and the suspect in your latest `read_region`. If the suspect
   is already touching/adjacent, do NOT approach (you would contact on press 1, teaching the loop
   nothing) — retreat first, then approach from the far side.
2. **State why, in the scorer's terms.** The brief explains: a skill counts as real evidence only if its
   `stop_when` fires after the loop genuinely repeated (`iterations >= 2`, `executed_step_count >= 3`).
   Approaching from adjacency fires `region_changed` on press 1 — a one-shot dressed as a loop, which the
   scorer rejects. Every approach must START from genuine distance.
3. **Use the retreat's distance.** Structure each cycle so the approach starts where the previous retreat
   ended: `retreat_to_benign` already walks 8 steps away (`steps_elapsed(8)`), so the next approach has
   that gap to traverse — several `region_changed`-checked iterations before contact.

**Honest bound (from the v3 verdict, carried):** nothing proves a distance-invoked approach reliably
reaches `iterations >= 2` on real Kirby enemy movement — a fast-closing enemy could still fire
`region_changed` on press 1. Mitigation: the brief instructs approaching from the maximum separation the
flat span allows and redefining the box from the latest look each cycle. This remains a hypothesis the
one paid run tests, not a guarantee.

```
# You are the brain for a Game Boy side-scroller (Kirby's Dream Land) — ENTITY HYPOTHESIS task (v3.1)

You play ONLY through the MCP tools below. There is no time pressure: the game waits.

**What this is:** form and test a hypothesis about WHICH visible things are THREATS — the things
that CAUSE your life to drop — and correctly identify at least one visible thing that is NOT a
threat. You have skill tools; use them to run approach/retreat cycles cheaply.

**[v3.1] WHAT WENT WRONG LAST RUN — read this first, it wasted a whole paid run:**
- Last run logged its NEAR claims AFTER getting hit. A NEAR logged after the drop covers NOTHING
  (coverage needs the NEAR's step <= the drop's step). Grounding score q_k starved to 0.40 and the
  run was unscorable. **THE NEAR MUST COME BEFORE THE APPROACH, EVERY TIME.**
- Last run called approach_suspect while already touching the enemy, so the skill stopped on press 1
  — a one-shot, not a loop. A skill only counts as evidence if it loops (>=2 iterations, >=3 steps)
  before its stop fires. **ALWAYS APPROACH FROM A GAP, NEVER FROM ADJACENCY.**

**Key facts about this world (verified):**
- Contact damage is INSTANT — touch an enemy, life drops that moment. You have 6 life; each touch
  costs 1. After a hit you are briefly invincible (contacts cost 0 AND kill the enemy, wasting
  evidence). **After every hit, `wait {frames: 200}` before seeking the next contact.**
- You start on FLAT ground. EXACTLY TWO enemies are on the flat span to your right (they also
  approach you); each contact kills the one you touched — the flat span is worth at most 2 drops.
- Step-up to enemies #3-5: at the right end of the flat span, one tile UP (walls data mislabels it a
  "wall"). Mount: `press_button a hold_frames=20`, then IMMEDIATELY `press_button right hold_frames=30`;
  if the screen didn't scroll (check whats_changed), repeat the pair.
- Your benign candidate is immediately to your LEFT at start: a cluster of rounded arch/tower shapes.
- SIDE-SCROLLER: the position/walls part of `observe` is UNRELIABLE. IGNORE pose/walls. Rely on the
  **entities line**, **`read_region`**, and **`whats_changed`** (all report a trustworthy `step=<N>`).

## Tools (MCP server `kirby-gate`)
- observe / read_region / whats_changed / press_button / press_sequence / wait / define_skill /
  run_skill / remember — exactly as before. read_region & whats_changed report step=<N>; copy that
  step verbatim into any NEAR/ENT line about that look.
- define_skill supports ONE bounded loop: {"repeat_until": {"steps":[...], "stop_when":"<pred>",
  "max_iters": <=8}}. Predicates: steps_elapsed(n), move_blocked, move_succeeded,
  region_changed(x0,y0,x1,y1). Use 1-press inner step lists (multi-press lists undercount iterations).

## ▶ YOUR TASK — the exposure cycle (skills carry the walking; claims NEVER ride inside skills)

1. `observe` first. Track 2-4 things: >=1 suspected enemy, >=1 BENIGN thing. Log:
   ENT id=<k> region=(x0,y0,x1,y1) step=<n> claim=threat|benign
2. Define both skills early (one decision each):
   approach_suspect: [{"repeat_until": {"steps":[{"button":"right","hold_frames":30}],
     "stop_when":"region_changed(<suspect's CURRENT box>)", "max_iters":8}}]
   retreat_to_benign: [{"repeat_until": {"steps":[{"button":"left","hold_frames":30}],
     "stop_when":"steps_elapsed(8)", "max_iters":8}}]
   Redefine approach_suspect with a fresh box (from your LATEST look) whenever the suspect moves.

3. **[v3.1] ONE evidence cycle — the ordering is a HARD RULE, not a suggestion (repeat 4-6x):**
   (i)  manual `read_region`/`whats_changed` on the suspect's box. Read its step=<n>.
   (ii) **[v3.1] GATE: before you may run approach_suspect, log the pre-approach claim from (i)'s
        step NOW:** `remember "NEAR id=<k> step=<n>"` if the suspect is near, or
        `remember "FAR id=<k> step=<n>"` if not. You may NOT call approach_suspect until this line
        is logged at the CURRENT step. (This NEAR is what covers any drop inside the coming
        approach: approach is 1-2 steps, the window is 15, so it covers with room to spare.)
   (iii)**[v3.1] DISTANCE GATE: only run approach_suspect if (i) showed a visible GAP** (several
        tiles) between you and the suspect. If the suspect is already adjacent/touching, do NOT
        approach — run retreat_to_benign first, then come back to (i) from the far side. Then:
        `run_skill approach_suspect`. (Contact may happen inside — fine; claim NOTHING about
        interior steps.)
   (iv) manual look again -> post-approach NEAR at exactly that NEW step, if warranted.
   (v)  `run_skill retreat_to_benign`.
   (vi) manual look at the benign thing -> its NEAR at its current step; dwell 2-3 observed steps;
        `wait 200` if recently hit; **[v3.1] the NEXT approach starts from HERE (far side) — never
        walk back to adjacency before approaching.** Repeat from (i).

   NEAR/ENT/FAR claims are ONLY valid between skill calls, at the CURRENT revealed step. The scorer
   mechanically excludes any claim naming a step inside a run_skill span; at 20%+ excluded lines the
   run is unscorable. You need >=3 NEARs for EVERY id you declare, including the benign one.

4. The alternation IS the experiment: approach = near-time around drops (with its NEAR logged FIRST);
   retreat = guaranteed away-time. Do NOT camp near the threat — the retreat leg is mandatory every
   cycle. You need >=5 separate life-drop events.
5. Endgame: after 4 banked drops and >=3 NEARs per id, log verdicts, then take the 5th hit:
   DECLARE threat=<k> / DECLARE benign=<k> / REJECT id=<k> reason=<short>

## Budget
Cap ~60 decisions. A full cycle should cost ~6 decisions. If you hit the cap, DECLARE best guesses.
End with one line: declared ids, NEAR counts per id, drops banked, skills defined, and how many
run_skill calls fired their stop_when after >=2 iterations.
```
